# Changelog

> *Generated by [aurora@aurora-smart-home (ha-integration-dev skill)](https://github.com/tonylofgren/aurora-smart-home)*

## 0.7.0 – 2026-11-14
- What if: the Settings tab estimates for 3, 5, 7, 14 and 30 days (and the value typed in) how much state history another global retention frees or adds. Own retention per entity is respected; events and statistics are not included. Shown even when the retention is set in your own YAML.
- Sudden heavy writers: the analysis learns each entity's usual rows per day (moving average, once a day). An entity that writes at least ten times as much and at least every 30 seconds, or a new entity that writes every 5 seconds, shows up in the database health card and as a repair issue. "Mark as normal" takes the new rate as usual. Excluded entities and entities kept for an hour only are not flagged.
- Debug logging left on: loggers set to debug (logger configuration, "Enable debug logging", `logger.set_level`) appear as a recommendation in the overview with the integrations and, once noticeable, the size of the log file.
- New WebSocket commands `storage_manager/retention_whatif` and `storage_manager/ack_writers`.

## 0.6.1 – 2026-11-14
- New **Settings** tab with the rules by kind of sensor, the recorder settings and a link to the integration options. Both cards were collapsed at the bottom of the database view before. The recommendations link to the rules.
- On phones the rules stack (selection below the text) and the active tab scrolls into view.

## 0.6.0 – 2026-11-14
- New sensors can get their kind's rule automatically: a switch per kind under *Database → Rules by kind of sensor*. It covers only entities created after the switch was turned on. The rule is applied after the first analysis that recognises the sensor, with no minimum size and no immediate purge. Your own settings, dismissals and usage protection come first, and each entity is set up only once. Logged in the history as "Rules applied to new sensors".
- `storage_manager/kind_rules` accepts `auto: {kind: true|false}`.

## 0.5.0 – 2026-11-14
- "Biggest savings" in the overview includes the open retention recommendations with what they free. It replaces the "N entities = X % of the database" hint, which only showed size, not savings. The header shows the retention savings next to the safely reclaimable bytes. They are freed by the nightly purge; the file only shrinks after a repack.
- Rules by kind of sensor are configurable in the database view: for each kind (diagnostic values, time and date, power, energy meters, GPS trackers, presence and distance, attribute-only updates, large attributes, very frequent values) choose another tier or no recommendation. Each kind shows how many entities match, their history size and what the rule saves. Power and energy meters cannot be set to "don't record"; other entities with statistics keep 1 day instead.
- New WebSocket command `storage_manager/kind_rules`.

## 0.4.1 – 2026-11-14
- Figures update after a cleanup: the storage breakdown from the Supervisor (cached for an hour) is read again after every cleanup, not only after deleting backups or files. Repacking the database now counts too.
- After a repack the database is analysed again, so the size history, the effect chart and the sizes per entity show the smaller file.
- The history shows "Recorder settings changed" instead of a raw key, and lists what each cleanup covered.

## 0.4.0 – 2026-11-14
- Rules by kind of sensor: power (3 days), energy meters (7 days), GPS trackers (7 days), time and date sensors (don't record), presence and distance sensors (1 day). Long-term statistics are always kept.
- Rules are judged per integration: many small sensors of one kind count together, so for example hundreds of Powercalc sensors get a recommendation even if none would alone. Usage protection still applies per entity.
- Four or more recommendations of the same kind from one integration show up as one line in the inbox, with the list of entities.
- Sensors that report more than once a minute carry a hint how to throttle them at the source (ESPHome, Powercalc, Shelly, generic).
- docs/sensor-rules.md explains every rule with its sources.

## 0.3.2 – 2026-11-14
- Safety check sized realistically: the room for deleting follows what is deleted (three times its size, at least 512 MB, at most half of the data) instead of half the file. Room for a new backup is taken from the newest backup with the database; only without one the file size is used. The preview shows both parts.
- Purging outdated rows needs no backup: Home Assistant deletes them every night anyway. History of deleted entities, orphaned statistics and per-entity purges still get one.

## 0.3.1 – 2026-11-14
- SQLite builds without `dbstat` (seen on Home Assistant OS): sizes are no longer raw estimates but scaled to the bytes in use in the file. The panel says so, and the reason is kept for the diagnostics.
- Repack: when no method fits, the panel shows the data in the file, what an ordinary repack and the RAM variant need, and how much space to free or how much data to remove for it to fit.
- The panel content starts at the left like the tabs instead of being centred on wide screens.

## 0.3.0 – 2026-11-14
- Safety chain before anything is deleted from the database: free-space check, full SQLite integrity check (a clean result is reused for three days), and a verified backup of Home Assistant with the database (a backup with the database from the last six hours is reused). A damaged database stops every deletion and raises a repair issue. The cleanup log names the backup and the deleted entities. Option *Back up before deleting from the database* (on by default).
- Cleanups run in a safe order: backups, files and Docker images first, then the database.
- Repack with little free space: the plan is measured from the file's free pages. Incremental repack in small steps, an ordinary repack, or one with the temporary copy in RAM; an ordinary repack can switch the file to incremental mode for the future.
- Analysis in steps with short read transactions, progress and a stop button. Attribute rows shared by several entities are split between them; loose attribute rows are counted.
- New recommendation reason: entities whose rows mostly change only attributes. The detail sheet shows which attributes keep changing.
- Health checks: database (WAL size, growth, integrity, statistics issues) and backup protection (schedule, newest backup, failed attempt, offsite copy, size, encryption, database included, free space, locations, emergency kit, restore test).
- SQLite table sizes use dbstat's aggregate rows and are cached for a day; MariaDB sizes are labelled as estimates.
- Detection of Home Assistant's native per-entity recorder option.
- 133 tests.

## 0.2.0 – 2026-11-14
- Database view rebuilt around decisions: a recommendations inbox with reasons, savings, accept or dismiss, and accept-all.
- Usage protection: automations, scripts, UI helpers that read history, the energy dashboard and dashboard history cards. Conflicting settings are flagged.
- Top causes (80 % of the size), a grouping by integration with group suggestions, and the full list.
- Detail sheet: rows per day, largest attributes, usage, and the impact of each retention level.
- Effect chart of the database size with markers for changes.
- Recorder settings in the panel (retention, commit interval, auto purge, auto repack). Keys already set in YAML are locked.
- Exclude filters for domains, patterns and event types, plus cleanup of exclusions that match nothing.
- Count of outdated rows and a purge-now action.
- 90 tests.

## 0.1.0 – 2026-11-13
First release: panel (overview, database, backups, files), byte-based database analysis, per-entity retention tiers, recorder exclusions via packages, local backup rotation, file scanner, growth forecast, sensors, buttons, repair issues, actions, diagnostics and GUI Recorder import.

Tested on Home Assistant 2026.10.4 with SQLite. Not yet field-tested: the Supervisor breakdown on Home Assistant OS, MariaDB/PostgreSQL and backup rotation with real backups. Feedback is welcome.
