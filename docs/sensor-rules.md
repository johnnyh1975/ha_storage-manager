# Rules by kind of sensor

> *Generated by [aurora@aurora-smart-home (ha-integration-dev skill)](https://github.com/tonylofgren/aurora-smart-home)*

Storage Manager recommends a shorter history per entity. Since 0.4 it also recognises common kinds of sensors and judges them **per integration**: 500 small power sensors are worth a recommendation together even if none of them is on its own. Usage protection still applies to every single entity (energy dashboard, history cards, helpers that read history).

## Principles

- **Shorten, don't exclude, when there are statistics.** Sensors with a `state_class` keep hourly long-term statistics forever; the energy dashboard and statistics cards use those. A shorter history keeps them, excluding an entity from the recorder removes them. ([History docs](https://home-assistant.io/components/history/), [community guide](https://community.home-assistant.io/t/how-to-keep-your-recorder-database-size-under-control/295795?page=9))
- **Rows times changing attributes is what costs space.** Unchanged attributes are stored once; a value and attributes that both change often grow the database fast. ([Sensor entity docs](https://developers.home-assistant.io/docs/core/entity/sensor))
- **Throttling at the source beats any retention.** ESPHome can send an average every minute (`throttle_average`) or periodic values plus large changes (`or: throttle + delta`); the recorder itself cannot filter values. ([example 1](https://community.home-assistant.io/t/esp-sensor-data-update/997508), [example 2](https://community.home-assistant.io/t/how-to-esphome-time-of-flight-sensor-reporting-every-5s-and-i-want-to-eliminate-small-variations-in-the-reported-value-yet-respond-to-a-large-change-on-next-update/598987), [recorder](https://community.home-assistant.io/t/reduce-recorded-amount-of-data-of-shelly-devices/994711))
- **Home Assistant already leaves out some attributes**: sun position, release notes of updates, the play position of media players, access tokens of cameras and images (checked in the 2026.10 source). Weather entities no longer carry the forecast in their state. No rule is needed for these.

## Rules

Since 0.5 every kind can be set to another tier or switched off under *Database → Rules by kind of sensor*. The rules only change the recommendations; nothing is applied until it is accepted and applied. Power and energy meters cannot be set to "don't record" because that would drop their statistics; for other kinds, entities with statistics keep 1 day instead.


| Kind | Recognised by | Recommendation | Why |
|---|---|---|---|
| Diagnostic values | entity category *diagnostic*, signal strength, RSSI, SSID, IP, uptime, firmware … | don't record; 1 day with statistics | history practically never used |
| Time and date | `time_date`, `worldclock`, template sensors named `time`, `date` … | don't record; 1 day with statistics | change every minute, no value in history |
| Power | device class *power*, state class *measurement*, more often than every 15 min | 3 days | statistics stay; often hundreds of sensors (Powercalc, plugs, inverters) |
| Energy meters | device class *energy*, state class *total*/*total_increasing*, more often than every 15 min | 7 days | the energy dashboard uses only long-term statistics |
| GPS trackers | `device_tracker` with `source_type: gps`, more than 48 rows/day | 7 days | every position stores coordinates; a map card with `hours_to_show` protects more |
| Presence and distance | device class *distance* or names like `moving_target`, more than once a minute | 1 day | mmWave sensors can report many times a second |
| Attribute-only updates | ≥ 80 % of rows change only attributes | 1 day; 3 days with statistics | see the detail sheet for the attribute that keeps changing |
| Large attributes | ≥ 60 % of the space is attributes | 1 day; 3 days with statistics | |
| Very frequent values | more often than every 5 minutes | 3 days | |

Router-based device trackers have no rule: their attributes (IP, MAC, host name) rarely change, so they are cheap unless an integration adds a changing attribute – which the attribute-only rule catches ([example](https://community.home-assistant.io/t/huawei-lte-integration-is-filling-up-db/199110)).

## Hints at the source

For sensors that report more than once a minute the recommendation carries a hint:

- **ESPHome**: `throttle_average` or `or: throttle + delta` filters.
- **Powercalc**: power sensors write only on change; energy sensors also every 10 minutes and groups are throttled – all adjustable (`energy_update_interval`, `group_power_update_interval`, …). ([Powercalc docs](https://docs.powercalc.nl/configuration/global-configuration/))
- **Shelly**: reporting interval and power threshold in the device's web interface.
- Other integrations: a longer polling or reporting interval, where the integration offers one.
