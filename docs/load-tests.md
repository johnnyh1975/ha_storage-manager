# Load tests

> *Generated by [aurora@aurora-smart-home (ha-integration-dev skill)](https://github.com/tonylofgren/aurora-smart-home)*

`tests/load/test_load.py` generates a recorder database straight into the recorder's own SQLite tables and runs the paths that touch many rows. Each phase has a time limit per million rows and a limit for how much the process's peak memory may grow, so a change that reads a whole table into memory, or a quadratic loop, fails there.

```bash
python -m pytest tests/load -q -s --load-rows=10000000
```

The generated data: 500 entities, one entity that no longer exists with 5 % of the rows, 50 attribute variants, and one event type with 10 % of the rows as events. Without `--load-rows` the load tests are skipped. CI runs them nightly with two million rows.

## Results (1.5.0, 10 million state rows)

Measured on a small cloud machine (2 cores, 8 GB RAM, SSD), SQLite, database file 2.5 GB.

| Phase | Rows | Time | Peak memory growth | Limit |
|---|---|---|---|---|
| Analysis (all entities, attributes, events) | 10,000,000 | 15.5 s | 35 MB | 60 s per million rows, 256 MB |
| Targeted backup for undo (export and verify) | 500,000 | 13.0 s | 5 MB | 60 s per million rows, 128 MB |
| History of the deleted entity (Home Assistant's purge) | 500,000 | 55.2 s | 38 MB | 240 s per million rows, 256 MB |
| Events of one type (in chunks) | 1,000,000 | 5.7 s | 63 MB | 60 s per million rows, 256 MB |

The load test found one slow path before 1.5.0: the targeted backup wrote every column of every row, NULL included; in a profile of 500,000 rows that took 1.6 times as long. Since 1.5.0 the file leaves NULL values out (format 2; files of format 1 still restore).

MariaDB and PostgreSQL run the regular test suite in CI; the load test generates SQLite only.
